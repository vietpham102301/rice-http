# M5 — Error Handling: Design

**Status:** approved, not yet implemented
**Date:** 2026-09-13
**Milestone:** M5 in [docs/04-roadmap.md](../../04-roadmap.md)
**Decision record:** [ADR-0002](../../adr/0002-handler-returns-error.md); this milestone
adds ADR-0008
**Depends on:** M4 (`Middleware`, `Build`, the compiled chain)

## Goal

Give rice one place where an `error` becomes a response, and make a panicking handler
survivable.

ADR-0002 fixed the handler signature in M1: `func(c *Ctx) error`, no abort flag, no
sentinel the framework inspects. M2 built a two-branch funnel to serve the 404 path.
M5 replaces that funnel with the real one — `HTTPError`, a configurable `ErrorHandler`,
and panic recovery — and adds `middleware/`, the first opt-in package.

## Question this milestone answers

Can one funnel handle every failure mode without special cases?

The M2 funnel could not: it carried an `errors.Is(err, ErrNotFound)` branch that existed
only because `ErrNotFound` was a plain `errors.New` value with no status attached to it.
M5 tests the claim by removing the branch rather than by asserting the claim is true.

## What the probe found, and why this milestone grew

`docs/03-core-concepts.md` §7 has said since M1 that "the core installs a panic hook on
the fasthttp server so a panicking handler produces a 500 and does not take the connection
down."

Both halves are false.

fasthttp v1.73.0 has no `PanicHandler` and no equivalent. Grepping the module finds exactly
one `recover()`, in `Response.writeBodyStream`, guarding body-stream writes.
`server.go:2621` calls `s.Handler(ctx)` bare, from a worker-pool goroutine that installs no
recovery of its own.

The consequence is worse than a dropped connection. Measured against `main` at `4f01ab6`,
with a handler that panics:

```
GET /ok   -> 200 <nil>
panic: handler exploded
...
github.com/vietpham102301/rice-http.(*App).handle(...)  app.go:113
github.com/valyala/fasthttp.(*Server).serveConnCounted(...)  server.go:2621
github.com/valyala/fasthttp.(*workerPool).workerFunc(...)  workerpool.go:225
exit status 2
```

The process dies. Every in-flight request on every other connection dies with it.

This is not a hypothetical rice inherited from a design document — it is the current
behaviour of the code on `main`, and it is the reason panic recovery in M5 is core
behaviour rather than an opt-in middleware.

## Non-goals

**405 Method Not Allowed.** A request with a known path and an unregistered verb returns
404 today, and will still return 404 after M5. Producing 405 requires the miss path to
probe the other per-verb trees before giving up, which spends time on every miss —
including the misses generated by scanners, which is most of them in production. The
roadmap does not ask for it in M5. Deferred, with this paragraph as the reason so it is
not re-litigated from scratch.

**JSON error bodies.** ADR-0006 keeps `encoding/json` out of package `rice`. A user's
`ErrorHandler` can emit RFC 7807 or anything else; the default emits `text/plain`.

**Per-group or per-route error handlers.** `03-core-concepts.md` §7 says "there is exactly
one such place, by design." M5 keeps that.

**Recovering a response that was already streamed.** A handler that calls
`SetBodyStreamWriter` and then returns an error has already put bytes on the wire that
`ResetBody` cannot recall. Documented as a known limit, not solved.

**Structured logging.** The default handler uses the standard `log` package. Anything more
is a reason to replace `ErrorHandler`, which is one line.

## Decisions

### D1: `HTTPError` is the one error type, and its fields are exported

```go
type HTTPError struct {
	Code    int    // HTTP status code
	Message string // sent to the client; empty means fasthttp.StatusMessage(Code)
	Err     error  // the real cause; never written to the response
}

func NewHTTPError(code int, msg string) *HTTPError
func (e *HTTPError) Error() string
func (e *HTTPError) Unwrap() error
```

One constructor, not two. Wrapping a cause is `&rice.HTTPError{Code: 400, Message: "bad
id", Err: cause}` — the fields are exported, so a second constructor taking three
arguments would be a synonym rather than a capability.

`Error()` renders `"<code>: <message>"`, and `": <cause>"` after it when `Err` is
non-nil. This string is what gets logged. It is never what gets sent.

`Unwrap` returns `Err`, so `errors.Is` and `errors.As` reach through an `HTTPError` to
whatever it wraps, and `fmt.Errorf("...: %w", httpErr)` reaches back the other way.

`Message` empty means `fasthttp.StatusMessage(Code)`. fasthttp supplies this, so rice does
not import `net/http` for one function.

### D2: `ErrNotFound` becomes a package-level `*HTTPError`, and the funnel loses its last special case

```go
// M2 through M4
var ErrNotFound = errors.New("rice: not found")

// M5
var ErrNotFound = &HTTPError{Code: 404, Message: "Not Found"}
```

This is the decision that answers the milestone's question. The M2 funnel had one branch
that existed purely because the sentinel carried no status:

```go
if errors.Is(err, ErrNotFound) {
	status = fasthttp.StatusNotFound
	body = "Not Found"
}
```

With the sentinel carrying its own code, `errors.As(err, &he)` handles the 404 exactly as
it handles every other error, and the branch is deleted rather than generalised. No error
is special to the framework.

It is also free. `ErrNotFound` is built once at package initialisation, so a 404 costs one
allocation — the `Ctx` — the same as a successful request. A service being scanned pays
nothing extra for being scanned.

The public type changes from `error` to `*HTTPError`. `errors.Is(err, rice.ErrNotFound)`
still works, because it is still the same pointer. `var e error = rice.ErrNotFound` still
compiles.

### D3: `PanicError` carries the value and the stack

```go
type PanicError struct {
	Value any    // the value passed to panic()
	Stack []byte // debug.Stack(), captured at recovery
}

func (e *PanicError) Error() string  // "panic: <value>"
func (e *PanicError) Unwrap() error  // Value if it implements error, otherwise nil
```

`debug.Stack()` runs only when something panicked. It costs microseconds and several
allocations, which is the correct price for an event that should not happen and that is
nearly impossible to diagnose without it. During a deferred call triggered by a panic the
panicking frames are still on the stack, so the trace points at the panic rather than at
the recovery.

`Unwrap` exists so `errors.As` can find a panicked error value. It also creates a trap,
which D5 closes.

### D4: The core recovers, in `handle`, outside everything

```go
func (a *App) handle(fctx *fasthttp.RequestCtx) {
	c := &Ctx{}
	c.reset(a, fctx)

	defer func() {
		if r := recover(); r != nil {
			a.callErrorHandler(c, &PanicError{Value: r, Stack: debug.Stack()})
		}
	}()

	h, ok := a.lookup(fctx.Method(), fctx.Path(), &c.params)
	if !ok {
		a.callErrorHandler(c, ErrNotFound)
		return
	}
	if err := h(c); err != nil {
		a.callErrorHandler(c, err)
	}
}
```

The deferred closure is written out rather than expressed as `defer a.recoverPanic(c)`
because this is the shape that was measured. A method-value defer may well be equivalent;
it has not been measured, and the hot path is not where an unmeasured equivalence gets
assumed.

This costs something on every request, including requests that never panic, which is a
deliberate exception to design principle 7 — "the hot path pays no cost for unused
features." ADR-0008 records the exception and its justification so that a later reader
does not remove it as an oversight.

The measured cost, `BenchmarkChainDispatch0`, eight runs each, both arms in one session:

| | median | range | allocs |
| --- | ---: | --- | ---: |
| no recover | 90.72 ns | 85.78 – 94.84 | 1 |
| always recover | 93.81 ns | 89.00 – 94.88 | 1 |

Median delta +3.09 ns, mean delta +1.85 ns, **ranges overlapping**. At n=8 this does not
resolve the cost; it bounds it at a few nanoseconds on a ~91 ns dispatch. The allocation
count is unchanged, which is the load-bearing part: an installed recovery that never fires
allocates nothing. M5 pins the number properly — see Benchmarks.

### D5: `DefaultErrorHandler` checks `*PanicError` before `*HTTPError`

**Corrected after execution.** Both this section's code block and its `respond` listing
below described code that no longer exists, because writing the M5 allocation budgets found
a problem this section did not anticipate: `errors.As(err, &target)` heap-allocates
`target`, because `&target` is passed as an `any` parameter (`go build -gcflags=-m` reports
`moved to heap`). Unfixed, a plain 404 or a fresh `HTTPError` would have cost two or three
times the allocations D2 promises. The fix, landed in `errors.go`, is a type switch on the
concrete types in front of the `errors.As` pair below:

```go
func DefaultErrorHandler(c *Ctx, err error) {
	switch e := err.(type) {
	case *PanicError:
		respondPanic(c, e)
		return
	case *HTTPError:
		if e.Err == nil {
			respond(c, e.Code, e.Message)
			return
		}
	}

	var pe *PanicError
	if errors.As(err, &pe) {
		respondPanic(c, pe)
		return
	}

	var he *HTTPError
	if errors.As(err, &he) {
		respond(c, he.Code, he.Message)
		return
	}

	log.Printf("rice: unhandled error: %v", err)
	respond(c, fasthttp.StatusInternalServerError, "Internal Server Error")
}
```

**Corrected again, in the M5 final whole-branch review.** The `*HTTPError` case above
originally answered unconditionally, and the review measured that this made D5's own rule —
a recovered panic is always a 500, never a client error — hold for some wrappings only:
`&HTTPError{Code: 400, Message: "m", Err: &PanicError{Value: "boom"}}` answered 400 through
this case, while the identical value wrapped once more in `fmt.Errorf("ctx: %w", ...)`
answered 500 through the fallback below, because only the wrapped form failed to match the
type switch and fell through to the `errors.As` pair where the `*PanicError`-before-`*HTTPError`
order actually runs. The `e.Err == nil` guard closes that gap: an `*HTTPError` that wraps
anything — a `*PanicError`, an ordinary error, anything — falls through to the same
`errors.As` pair a handler-wrapped error already takes, so the panic-always-wins ordering
governs every wrapping uniformly rather than only the ones that happen to miss the fast path.

`ErrNotFound` and a fresh `NewHTTPError` both leave `Err` nil, so they still match the type
switch directly: the 404 path stays at 1 allocation and the `HTTPError`-return budget stays
at 2, unchanged by this guard. Only an `*HTTPError` that actually carries a cause pays for the
walk it needs.

The type switch matches every error the funnel produces with no cause of its own —
`ErrNotFound`, a fresh `NewHTTPError`, the `*PanicError` built in `handle` — without
allocating, and it exists for allocation, not correctness, but only because of that guard:
without it, the switch's `*HTTPError` case would decide a case the `errors.As` ordering below
was written to own. A handler-wrapped error, or an `*HTTPError` that wraps a cause of its own,
pays for the `errors.As` walk below it — the case that genuinely needs it. `respondPanic`
holds the panic-logging body once, shared by both paths.

The `*PanicError`-before-`*HTTPError` order still applies in the fallback, and for the same
reason as before: `PanicError.Unwrap` returns the panicked value, so
`panic(rice.NewHTTPError(400, "x"))` would otherwise produce a 400 through the fallback — a
panic quietly becoming a client error. A panic is a bug, not a way to signal failure, and it
is always a 500. A type switch matches on exact dynamic type, so this ordering concern is
specific to the `errors.As` fallback; between the type switch's two cases there is no ordering
question left to have, now that the `*HTTPError` case only ever matches a value the fallback
would have answered identically.

`respond` is unexported and does the same three things every time, plus one guard added in the
same review:

```go
func respond(c *Ctx, code int, msg string) {
	if v := validStatus(code); v != code {
		log.Printf("rice: invalid HTTP status code %d, replacing with %d", code, v)
		code = v
	}
	if msg == "" {
		msg = fasthttp.StatusMessage(code)
	}
	c.fctx.SetStatusCode(code)
	c.fctx.SetContentType(MIMETextPlainUTF8)
	c.fctx.SetBodyString(msg)
}
```

**`validStatus`, added in the M5 final whole-branch review.** `&HTTPError{Message: "nope"}` —
`Code` omitted, which `HTTPError`'s own doc comment shows as the ordinary way to build one
when there is no cause to wrap — answered 200, because fasthttp's
`ResponseHeader.StatusCode()` reports `StatusOK` for a zero status and nothing in `respond`
checked the code it was given. A handler returning an error getting a success status defeats
the funnel's whole premise. `validStatus(code int) int` replaces anything outside 100–599
(`StatusContinue` through the top of the range HTTP defines) with 500 and is used by both
`respond`, before writing, and `HTTPError.Error()`, so `&HTTPError{}.Error()` now reads
"500: Internal Server Error" instead of "0: Unknown Status Code" — the string it renders
matches what a client sent through `respond` actually receives. `respond` logs the value it
replaced rather than replacing it silently, and replaces rather than panics: the funnel's job
is to terminate a request no matter what it is handed, and panicking over a bad status code
inside the funnel would turn one bad handler into a dead request path instead.

There is deliberately no explicit `ResetBody()` call here. This section originally specified
one, on the theory that it enforces ADR-0002's rule — that a handler which writes a body and
then errors has it discarded. It does not enforce anything: `SetBodyString` already calls
`closeBodyStream`, then `bodyBuffer()` (which nils `bodyRaw`), then `Reset()`, so no input to
`respond` exists under which the explicit call changes observable behaviour. It was found
during M5 by a fault injection that removed the call and produced no failure — the injection
working as designed, not a gap in the guard. ADR-0002's rule still holds; it always held via
`SetBodyString`, and the extra call was never doing the work its comment claimed.

`DefaultErrorHandler` is exported so a custom handler can delegate to it for the cases it
does not care about.

### D6: The cause is logged to stderr; there is no separate hook

`03-core-concepts.md` §7 promised "the configured error hook". No such hook is defined
anywhere in the documents, and M5 does not add one.

The default handler logs unrecognised errors and recovered panics with the standard `log`
package. Anything else — a structured logger, a sink, sampling, dropping — is a reason to
replace `ErrorHandler`, and replacing it is exactly as much work as configuring a hook
would have been. A second configuration point would contradict "there is exactly one such
place, by design" in the same document that promises it.

Cost accepted: package `rice` imports `log`, and rice's own test suite is noisy unless a
test replaces the handler. Tests that exercise the 500 path replace it.

### D7: `ErrorHandler` is set with an `Option` at construction

```go
type ErrorHandler func(c *Ctx, err error)

func WithErrorHandler(h ErrorHandler) Option

app := rice.New(rice.WithErrorHandler(myHandler))
```

`type Option func(*App)` has existed in `app.go` since M1 with no exported option to fill
it. This is the first genuine need.

Construction-time configuration cannot race with serving, so it needs no `built` guard and
no mutex, and `handle` reads `a.errorHandler` without synchronisation. A setter would need
a guard; an exported field would be an unguardable data race on a value read by every
failing request.

`New` assigns `DefaultErrorHandler` before applying options, so `a.errorHandler` is never
nil and the dispatch path never checks for nil.

`WithErrorHandler(nil)` panics at the call, in the style of every other registration
error: `rice: WithErrorHandler: handler is nil`.

### D8: `callErrorHandler` is the last-resort net

**Corrected after execution.** This section originally showed the last-resort response
written with raw fasthttp calls, including its own `ResetBody`, "so that a bug in rice's own
response path cannot recurse." That rationale does not hold up: `respond` is three fasthttp
calls with no path back into error handling, so it cannot recurse into anything. Acting on a
false rationale walked the implementer into reintroducing, in a second place, the exact
`ResetBody` no-op D5's correction above had just removed from the first. The code now calls
`respond`, like everything else in the funnel:

```go
func (a *App) callErrorHandler(c *Ctx, err error) {
	defer func() {
		if r := recover(); r != nil {
			log.Printf("rice: ErrorHandler panicked: %v", r)
			respond(c, fasthttp.StatusInternalServerError, "Internal Server Error")
		}
	}()
	a.errorHandler(c, err)
}
```

Without it, a panic inside the user's `ErrorHandler` reintroduces exactly the disease this
milestone cures — and reintroduces it in its worst form, because it only fires when
something has already gone wrong, which makes it intermittent and hard to reproduce.

It is free on the hot path: a request that succeeds never calls this function. Every call
site of the error funnel goes through it, so `a.errorHandler` is never invoked directly.

The last-resort response now goes through `respond`, the same one every other error in the
funnel uses. There is only one way this framework writes an error body; a second one would
just be a second thing to keep correct — which is the opposite of what the original
rationale was reaching for.

### D9: `middleware.Recover` ships, and does something the core cannot

```go
package middleware

func Recover() rice.Middleware {
	return func(next rice.Handler) rice.Handler {
		return func(c *rice.Ctx) (err error) {
			defer func() {
				if r := recover(); r != nil {
					err = &rice.PanicError{Value: r, Stack: debug.Stack()}
				}
			}()
			return next(c)
		}
	}
}
```

The named return `err` is the whole mechanism: the deferred function overwrites the return
value, so the panic leaves the chain as an ordinary error.

That is the difference from core recovery, and it is concrete. Middleware registered
*outside* `Recover` observes a returned error instead of an unwinding stack. A middleware
written as

```go
err := next(c)
record(err)
return err
```

sees the panic. Without `Recover`, `record` is skipped entirely, because unwinding does not
run that line. Core recovery cannot provide this: it sits outside the whole chain, and by
the time it runs, every middleware frame is gone.

`middleware/` also establishes the opt-in package layer that `02-architecture.md` describes
and nothing has used yet. The import direction is `middleware` → `rice`, which is legal
because `middleware/` is not under `internal/`. A user who does not import it pays nothing,
which is the point of putting it in its own package.

## Components

| Unit | Responsibility | Depends on |
| --- | --- | --- |
| `errors.go` | `HTTPError`, `PanicError`, `ErrNotFound`, `ErrorHandler`, `DefaultErrorHandler`, `respond` | fasthttp status codes, `log` |
| `app.go` | `errorHandler` field, `WithErrorHandler`, the deferred recovery in `handle`, `callErrorHandler` | `errors.go` |
| `middleware/recover.go` | `Recover()` | package `rice` |

`errors.go` grows from 14 lines to roughly 120. It stays one file: the types and the one
function that consumes them change together, and splitting them would put the funnel's two
halves in two places.

## Allocation budgets

| Operation | Budget | Status |
| --- | ---: | --- |
| Recovery installed, nothing panics | 0 extra | TARGET M5 |
| 404 through the funnel, prebuilt `ErrNotFound` | 1 (the `Ctx`) | TARGET M5 |

| Panic recovered, stack captured | documented, not bounded | TARGET M5 |

The first row is the one that must hold. It is asserted with `testing.AllocsPerRun`, not
read off a benchmark.

## Testing

**The funnel.**
- A handler returning `NewHTTPError(418, "teapot")` produces 418 and that body.
- A handler returning `&HTTPError{Code: 400, Message: "bad", Err: cause}` produces 400,
  and `cause.Error()` appears nowhere in the response.
- A handler returning a bare `errors.New("boom")` produces 500 and the generic body.
- `fmt.Errorf("wrapping: %w", NewHTTPError(404, "gone"))` produces 404 — `errors.As`
  reaches through.
- An `HTTPError` with an empty `Message` uses `fasthttp.StatusMessage(Code)`.
- A miss produces 404, and the funnel contains no branch naming `ErrNotFound` — asserted
  by the code, verified by the reviewer, not by a test.
- A handler that writes a body and then returns an error: the body is discarded. This test
  exists from M1 and must still pass.

**The cause never leaks.** One test builds an error chain whose cause string is a
distinctive token, drives every funnel path, and asserts the token appears in no response
body. This is the roadmap's exit criterion and it gets its own test rather than an
assertion tacked onto another.

**Panics.**
- A panicking handler produces 500.
- The process survives — the test issues a second request afterwards and asserts it
  succeeds. This is stronger than the roadmap's "without dropping the connection", because
  the probe showed the real failure is process death.
- A second request on the *same* keep-alive connection succeeds.
- A panic with a non-error value (`panic("boom")`, `panic(42)`) is handled.
- A panic inside middleware, not the handler, is recovered the same way.
- `PanicError.Stack` is non-empty and names the panicking function.
- A custom `ErrorHandler` receives a `*PanicError` and can inspect `Value`.

**The last-resort net.** An `ErrorHandler` that panics produces a 500 and the process
survives.

**Configuration.**
- `WithErrorHandler` replaces the default; the custom handler's response is what arrives.
- `WithErrorHandler(nil)` panics at the call.
- With no option, `DefaultErrorHandler` is in effect.

**`middleware.Recover`.**
- A panic inside it becomes a `*PanicError` returned normally.
- Middleware registered outside it observes that error as a return value — the test uses a
  recording middleware and asserts the record happened, which is the property that
  distinguishes `Recover` from core recovery and the only reason the package exists.
- With `Recover` installed, the core's recovery never fires. Asserted by a custom
  `ErrorHandler` that distinguishes the two paths.

**Allocation.** `TestAllocBudgetDispatchWithRecover` asserts the installed recovery adds
nothing, and `TestAllocBudget404` asserts the miss path costs exactly one.

**Fault injection.** Every guard above is broken on purpose and watched to fail, for the
reason M4's retrospective gives at length. In particular: the "cause never leaks" test must
be shown to fail when the default handler is changed to write `err.Error()`, and the
"process survives" test must be shown to fail when the deferred recovery is removed.

## Exit criteria

1. `errors.As` reaches through wrapped errors to `*HTTPError`.
2. A custom `ErrorHandler` replaces the default behaviour.
3. A panicking handler produces 500, and the process survives to serve the next request.
4. A test asserts the cause string never appears in any response body.
5. The funnel contains no branch special-casing any individual error value.
6. `AllocsPerRun` shows the installed recovery adds no allocation.
7. `make lint`, `make test`, `make cover` and `make bench` all exit 0; coverage does not
   drop below 98.4%.

## Open questions

None. The three that were open — whether to add the promised error hook, how
`ErrorHandler` is configured, and whether the core recovers — were settled in
brainstorming and are recorded as D6, D7 and D4.
